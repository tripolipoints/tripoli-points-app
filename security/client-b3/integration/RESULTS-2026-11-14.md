## Findings

1. **HIGH — stored script injection through the shop logo (client + server).**
   - `merchant_set_logo` stores any string, with no admin review. Only the shop's own phone + PIN is needed.
   - `tpStoreLogoHtml()` (index.html:2482) puts it into `src="…"` **without escaping**. Rendering the app's own function
     with a logo of `x" onerror="…"` gives `<img src="x" onerror="…" … onerror="this.onerror=null…">`. The injected
     handler comes first, and browsers use the first duplicate attribute, so the script would run for every customer or
     admin who opens that shop. It could then read the in-memory session.
   - The map pins are safe (`safeLogoUrl()`); the store page / list logo is not.
   - **The same line is on `main` @ `a54a85c` (Production V3.7.4).** Production was not queried or changed in this session.
   - Staging: 0 merchants have a logo, 0 suspicious values.
   - Proposed fix (needs approval):
     - client: `src="${esc(tpStoreLogoSrc(m))}"` and use `safeLogoUrl()` inside `tpStoreLogoSrc`;
     - server: `merchant_set_logo` accepts only `https://<project>.supabase.co/storage/…` URLs without quotes or angle brackets;
     - Production: a read-only check of the stored `logo_url` values, then a hotfix decision.
2. **Weak merchant PIN accepted on admin reset (low).** Only the length (4) is checked. Proposed: the same weak-PIN rule
   used for the 6-digit staff PIN (no repeated or sequential digits). This is a policy choice for you.
3. **Two lock counters protect the primary admin PIN (low).** `admin_login` (by username) and the October key `admin:<id>`
   (reset/wipe) count separately, so a guesser gets 5 + 5 attempts per window. Whoever knows the admin's id can also
   lock reset/wipe for a while. The id is only returned after an admin login. Proposed: one shared key, or move the
   PIN reset to a session-based `_v2` like the other admin actions.
4. **Sales depend on the old top-up wallet (decision dependency, not a bug).** `_tx_quote` refuses any sale whose reward
   is not covered by `merchant_wallet().avail` (old top-ups), even with no points redeemed and a full new allowance. On
   Staging today: the 2 active test shops have old-wallet balance 20 and new allowance 0; the pending shop has 0/0. This
   ties directly to the open decision «علاقة محفظة الشحن القديمة بـ §02». Until it is decided, every new shop needs an
   old-wallet top-up to sell.
