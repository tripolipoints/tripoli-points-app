# Tripoli Points — المرحلة 0 (v1.2): تقرير الاختبارات · 2026-11-11

النتائج كلها من نسخة محلية (PostgreSQL 16) تطابق Production اليوم. **لم يُنفَّذ أي SQL على Staging أو Production، ولم يتغيّر `main`.**

## ما الذي تغيّر

| الطلب | الحل |
|---|---|
| ملف الرجوع كان يعيد دوال PIN بلا حدّ محاولات | صار `tp-security-phase0-urgent-rollback.sql` ملفاً تشغيلياً آمناً. لا يحتوي أي تعريف دالة ولا أي `grant`. يفكّ الأقفال (للكل، أو لحسابات محددة في `v_keys`)، ثم يعيد فحص كل الحمايات **سلوكياً**. إذا كانت حماية ناقصة يتوقف ولا يغيّر شيئاً. على قاعدة لم تُطبَّق عليها المرحلة 0 يرفض التشغيل. في رأس الملف جدول «المشكلة ← الحل». |
| `admin_wipe_all_data` قابلة للاستدعاء بالمفتاح العام | **مغلقة على كل مفاتيح الـ API** (anon وauthenticated وservice_role)، حتى مع Admin ID وPIN صحيحين. زر «مسح كل البيانات» في التطبيق يتوقف حتى المرحلة 1. |
| الحفاظ على إمكانية الاستعادة | أي مسح ينسخ أولاً كل الجداول المتأثرة إلى schema خاص اسمه `tp_backup`، ولا يصل إليه أي مفتاح API. الاستعادة من محرر SQL فقط: `select public._tp_wipe_restore('<stamp>');`. تعيد الجداول الأب أولاً، وتحافظ على المعرّفات، وتوقف الـ triggers مؤقتاً، وتضبط الـ sequences. بعدها تقارن كل جدول بنسخته (عدد الصفوف + checksum)، فإذا اختلف أي جدول تتراجع عن كل شيء. ترفض الاستعادة إذا استُعمل التطبيق بعد المسح، فلا دمج صامت للبيانات. |
| المسح من التطبيق لاحقاً (المرحلة 1) | `admin_wipe_all_data_v2(p_session, p_pin, p_confirm)` تشترط: جلسة أدمن **أساسي**، والمفتاح `admin_wipe_enabled = 1` (القيمة الافتراضية 0، ويغيّره صاحب المشروع فقط من محرر SQL، وليس موجوداً في `admin_set_setting_v2`)، وعبارة «امسح كل البيانات»، وPIN مع حدّ المحاولات المشترك `admin:<id>`. ينطفئ المفتاح وحده بعد كل مسح، ويُسجَّل المسح مع رقم النسخة. |
| اختبارات سلوكية وليست بحثاً في نص الكود | `_phase0_selfcheck()`: الملف يستدعي الدوال فعلياً بدور anon ثم authenticated داخل خطوة يتم التراجع عنها، ويتوقف إذا فشل أي فحص. دالة يجدها مفتوحة يبلّغ عنها ولا يستدعيها، فلا يحصل أي أثر جانبي. |

### ماذا تغطي اختبارات المرحلة 0 السلوكية (55)

- **مصفوفة الصلاحيات:**
  - anon وauthenticated مرفوضان (42501) على كل الدوال المغلقة (20 دالة محلياً؛ أكثر على Staging لأن فيها نسخ التسجيل القديمة).
  - المسح مرفوض لهما حتى مع أدمن أساسي حقيقي وPIN صحيح.
  - لا يستطيعان قراءة جدول الأقفال، ولا الكتابة فيه، ولا مسحه، ولا فكّ القفل عبر `_rl_reset`، ولا فتح `tp_backup`.
  - لم تُحذف أي بيانات.
- **service_role:**
  - يبقى قادراً على `whish_confirm_payment` و`_expire_topup_orders`.
  - مرفوض على المسح، والاستعادة، و`tp_backup`.
- **التطبيق الحالي** يعمل بدور anon: دخول الزبون والتاجر والأدمن، فحص الرقم، والتسجيل.
- **الأقفال:**
  - 4 محاولات خاطئة ثم PIN صحيح تصفّر العدّاد.
  - المحاولة الخاطئة الخامسة تقفل الحساب حتى مع PIN صحيح، وقفل حساب لا يؤثر على حساب آخر.
  - الرقم غير الموجود محدود أيضاً، وتغيير الأحرف الكبيرة والصغيرة في اسم الأدمن لا يتجاوز القفل.
  - القفل ينتهي بعد مدته، وتسجيل الدخول الناجح يمسح السجل.
  - تبقى حدود أكتوبر للتاجر و`admin_reset_merchant_pin`، والمفتاح المشترك يوقف المسح أيضاً.
- **المسح والاستعادة (طريق المالك):**
  - النسخة تحتوي كل الجداول بنفس عدد الصفوف.
  - بعد الاستعادة: نفس الصفوف ونفس الـ checksum لكل جدول.
  - استعادة نفس النسخة مرة ثانية مرفوضة، والاستعادة مرفوضة إذا وُجدت صفوف جديدة.
  - حذف النسخة يزيل جداولها ويُبقي سجلها.

### اختبار عكسي (للتأكد أن الاختبارات تكتشف الخطأ)
- فتحنا `admin_wipe_all_data` و`customer_reset_pin` لـ anon، وجدول الأقفال لـ authenticated: الاختبارات فشلت في البنود الصحيحة.
- أعدنا `customer_verify_pin` القديمة بلا حدّ: فشل بندا القفل.
- فتحنا المسح ثم شغّلنا ملف الرجوع: توقف وقال «STOP — 2 protection(s) missing».

## ملاحظات قبل Staging
- **الاختبارات لـ Staging فقط:** `tp-security-phase0-tests.sql` يمسح الجداول ويعيدها داخل transaction تنتهي بـ ROLLBACK، فتبقى الجداول مقفلة بضع ثوانٍ.
- **إذا ظهر «permission denied to set role»:** الفحص الذاتي يحتاج أن يكون `postgres` عضواً في anon وauthenticated، وهذا الوضع الافتراضي في Supabase. إذا ظهرت هذه الرسالة على Staging، أرسلها لي.
- **ملف الحالة** `tp-security-status-check.sql` يبقى للقراءة فقط، وأضفنا له 6 بنود p0: إغلاق المسح على كل المفاتيح، النسخ قبل المسح، إغلاق `tp_backup`، والفحص الذاتي. الإثبات السلوكي بعد التطبيق يكون بهذا الاستعلام، والنتيجة الصحيحة صفر صفوف:

  ```sql
  select * from public._phase0_selfcheck() where not ok;
  ```
