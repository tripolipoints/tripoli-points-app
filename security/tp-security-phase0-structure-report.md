# Tripoli Points — حفظ بنية Staging قبل المرحلة 0 · تقرير مختصر · 2026-11-11

## الخلاصة

- **هل نستطيع تنفيذ المرحلة 0 بأمان؟** نعم، بعد خطوة واحدة: تصدير بنية Staging (قراءة فقط، دقيقتان) وتأكيدي أنه يُعاد بناؤه بنجاح.
- **لماذا هذه الخطوة؟** ملفات GitHub **لا تكفي** لإعادة بناء Staging.
- **هل يحذف ملف المرحلة 0 شيئاً؟** لا، فهو لا يحذف بيانات ولا جداول.
- **إصلاحات أكتوبر:** محفوظة كما هي.

## 2. الحل: تصدير البنية فقط

- **الملف:** `tp-structure-export.sql`. استعلام SELECT واحد، يُشغَّل من SQL Editor، بلا كلمة سر وبلا Docker. النتيجة CSV فيها أمر SQL في كل صف، بالترتيب.
- **ما يحفظه:** الامتدادات، الأنواع، الـ sequences، الجداول (أعمدة وقيم افتراضية وidentity)، **كل الدوال بكودها الكامل**، القيود، الفهارس، الـ views، الـ Triggers، تشغيل RLS وسياساته، صلاحيات كل دور على كل schema وجدول ودالة، الصلاحيات الافتراضية، جداول Realtime، إعدادات Storage buckets وسياساتها، مهام pg_cron، وصفوف الإعدادات الثلاثة.
- **ما لا يحفظه (عن قصد):** بيانات الزبائن والتجار والمحافظ والمعاملات، حسابات الأدمن، رموز PIN، كلمات السر، المفاتيح.
- **الاختبار المحلي:**
  - أُعيد بناء قاعدتين انطلاقاً من التصدير، ثم قورنتا بالأصل (`pg_dump -s`): الأولى مثل Production اليوم، والثانية بعد المرحلة 0 و1 والبريد (1589 أمراً، مع schema مخصّص وTriggers وأعمدة identity).
  - **النتيجة:** البنية متطابقة. مصفوفة صلاحيات anon وauthenticated وservice_role متطابقة. الفحص الذاتي للمرحلة 0 على القاعدة المعاد بناؤها: 52/52. صفوف الإعدادات عادت. لا بيانات زبائن. لا كلمات سر ولا مفاتيح في الملف.
  - **الفرق الوحيد:** ترتيب أسطر GRANT داخل نفس الدالة، والمعنى واحد.
- **حدود لم أتحقق منها:** المخططات الداخلية لـ Supabase (auth وstorage وrealtime) لم تُصدَّر، لأن أي مشروع Supabase جديد ينشئها بنفسه. واختبرت على PostgreSQL 16 محلياً، بينما Staging على 17.

## 3. ملف المرحلة 0 لا يحذف شيئاً

راجعت كل أمر حذف أو تعديل في `2_tp-security-phase0-urgent.sql` (البصمة `140f1b06…` لم تتغيّر):
- **أوامر تُنفَّذ فعلاً:**
  - `drop trigger if exists` على جدول جديد في `tp_backup`.
  - `drop function if exists public._tp_wipe_drop(text)`، وهي غير موجودة على Staging.
  - لا يوجد غيرهما.
- **أوامر داخل أجسام الدوال فقط، لا تُنفَّذ عند التطبيق:**
  - `truncate` موجود فقط داخل `admin_wipe_all_data`، وهي مغلقة على كل مفاتيح API، وتنسخ البيانات قبل أي مسح.
  - `delete` و`drop table` موجودان فقط داخل دوال الاسترجاع وحذف النسخ، وهي للمالك فقط، وحذف نسخة يتطلّب عبارة تأكيد مكتوبة.
- **الفحص الذاتي:** يضيف حساب تجربة داخل خطوة تُلغى فوراً.
- **التدريب المحلي:** بصمة البيانات قبل التنفيذ وبعد التسلسل الكامل (الملف، الفحوص، الاختبارات، الرجوع) **متطابقة**.

## 5 و6. التنفيذ والفحوص والأخطاء

التفاصيل في `00_RUNBOOK_Staging.md`. القسم أ صار «حفظ البنية» بدل النسخة الكاملة. باقي الأقسام كما هي:
- **ب:** قراءة قبل التنفيذ.
- **ج:** التنفيذ.
- **د:** 9 فحوص بعده.
- **هـ:** الأخطاء.

**إذا تعطّل Staging ولم ينفع إعادة تشغيل الملف:**
- أبني ملف إعادة تجهيز من تصدير البنية مع المرحلة 0، ويُطبَّق بعد موافقتك.
- البنية والإعدادات تعود كما كانت، أما البيانات التجريبية فلا تعود، وهذا مقبول حسب قرارك.

## 7. الشحن اليدوي: خطة عاجلة منفصلة

- **المشكلة:** `admin_topup_merchant` و`admin_resolve_topup_order` و`admin_mark_order_collected` لا تطلب أي إثبات أن المستدعي أدمن، ويمكن استدعاؤها بالمفتاح العام. يعني أي شخص يستطيع إضافة رصيد لمحفظة تاجر.
- **الاقتراح:**
  - **(أ)** مباشرة بعد نجاح المرحلة 0: إغلاق مؤقت لهذه الدوال، ويتم الشحن من SQL Editor عبر دالة للمالك فقط مع سجلّ لكل عملية.
  - **(ب)** لاحقاً: جلسات الأدمن من المرحلة 1.
- أجهّز ملف الخطة (أ) عند طلبك. لا شيء منه مُطبَّق أو مُعدّ للتشغيل الآن.
